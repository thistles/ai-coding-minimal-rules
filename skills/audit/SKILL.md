# 审：双轴审查

**只盯代码质量是不够的。** 一份改动要同时过两关，它们互相不能替代：

- **规范轴**：符不符合这个项目自己定的规矩？
- **规格轴**：符不符合这次一开始说清要做什么？

## 为什么必须分成两轴

- 代码漂亮但做错了事 → 规范过、**规格挂**
- 代码实现了规格但违背项目约定 → 规格过、**规范挂**

混在一起报，会互相掩盖：写法问题一多，真做错的那条就被淹了。

分开报，读者一眼能看出这次是**方向问题**还是**手艺问题**。

## 步骤 1：钉住比较基准

用户没说跟谁比就问一句（`main`？某个 commit？某个 tag？）。

```bash
git diff <基准>...HEAD        # 三点：比的是共同祖先
git log <基准>..HEAD --oneline
```

基准解析不了、或 diff 是空的，**在这里就停下报错**——不要带着空 diff 往下走。

## 步骤 2：找规格

按顺序找，找到就停：

1. 提交信息里的 issue 引用
2. 用户给的路径
3. 与分支名/功能名对得上的 `docs/spec.md`
4. 都找不到 → 问用户。**没有规格就直接跳过规格轴**，并在报告里写明"无可用规格"，不要自己脑补一个。

## 步骤 3：找项目规范

仓库里任何说明了"代码该怎么写"的东西：`AGENTS.md`、`CONTRIBUTING.md`、lint 配置、`docs/` 下的规范。

**仓库自己的规矩永远优先于任何通用风格建议。**

另外，即便仓库什么都没写，也按下面这 12 条代码坏味道过一遍。每条只写「可能存在」的判断，不写成硬性违规：

| 味道 | 怎么修 |
|---|---|
| 神秘命名 | 改名。起不出诚实的名字，说明设计不清楚 |
| 重复代码 | 抽出共同形状，两边都调它 |
| 依恋情结 | 把方法搬到它更关心的数据那边 |
| 数据泥团 | 打包成一个类型 |
| 基本类型偏执 | 给领域概念一个自己的类型 |
| 重复的 switch | 换多态，或抽成两边共用的映射表 |
| 霰弹式修改 | 一个逻辑改动散在多文件 → 收进同一个模块 |
| 发散式修改 | 一个文件因为多个不相干原因被改 → 拆开 |
| 过度设计 | 删掉。规格没要求的抽象就是负债 |
| 消息链 | 把 `a.b().c().d()` 藏进一个方法 |
| 中间人 | 只做转发的类/函数 → 删了直连 |
| 拒绝继承 | 大量覆盖父类 → 改用组合 |

判断标准永远是**判断题不是判决题**：仓库规矩压过坏味道；工具（lint、类型检查）已经管了的直接跳过。

## 步骤 4：两个轴分别报（可并行）

**规范轴**报告：

- (a) 每一处违反项目已成文规范的地方——**引用规范出处（文件 + 规则原文）**
- (b) 上面 12 条里你发现的坏味道——命名 + 引用对应 diff 片段
- 明确区分**硬违规**（违反成文规范）和**判断题**（坏味道）
- 400 字以内

**规格轴**报告：

- (a) 规格要求了但没实现 / 实现了一半的地方
- (b) diff 里做了但规格没要求的地方（范围蔓延）
- (c) 看着实现了但实现方式可疑的地方
- 每条都要**引用规格原文那一行**
- 400 字以内

## 步骤 5：汇总

按 `## 规范` / `## 规格` 两段分开列，**不要合并、不要重排**。

结尾一句话：每个轴各有几处问题，各自最严重的那一条是什么。**不要跨轴评出一个总冠军**——不许跨轴排序正是分开报的意义。

## 完成后

- 修规范轴里的**硬违规**（成文规范违反）。
- 坏味道是判断题，要不要改问用户。
- 规格轴的 (b) 范围蔓延通常要真删，不能只是嘴上承认。

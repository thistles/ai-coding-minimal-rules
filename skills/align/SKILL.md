# 对齐：把决定变成文件

对齐的产出只有三个，**都在仓库里，不在对话里**。对话会蒸发，文件不会。

## 产出

| 产物 | 位置 | 什么时候写 | 里面只有 |
|---|---|---|---|
| 项目宪法 | `AGENTS.md`（根目录） | 项目第一版，之后很少动 | 不可越界的红线 + 怎么构建怎么测 + 术语 |
| 本版规格 | `docs/spec.md` | 每次开工前 | 这一版做完长什么样、验收清单 |
| 决策记录 | `docs/adr/NNNN-xxx.md` | 决定成型时，**仅在满足三条时** | 一个决定 + 为什么 |

不要新增第四类文件。没有进展日志、没有架构图、没有 README 摘要。

---

## 步骤 1：先查事实，别问人

**能靠读代码、grep、读文件得到的答案，一律自己去查，不许问用户。**

用户的时间比你贵，而大部分"这个逻辑现在是怎么跑的"是可以直接读出来的。
读不出来的问题才值得占用一次提问。

## 步骤 2：一次一问，穷尽决策树

把这次要做的事当成一棵**决策树**：每个决定下面挂着它依赖的决定。

- **一次只问一个问题。** 一次抛五个问题会得到五个敷衍的回答。
- **每个问题都带上你的推荐答案。** 让用户只需说「就按你说的」，而不是从零构思。
- **深度优先。** 一个分支问到底再开下一个分支。
- **问完总结一遍**，用户确认「达成共识」之后才允许动手。

问题按这个顺序走（领域 → 技术 → 界面），能跳过的跳过：

1. **领域**：这个词在我们这儿到底指什么？边界在哪？
2. **行为**：什么情况算做完？拿什么验收？
3. **技术**：要不要动技术栈？动了以后换回来贵不贵？
4. **范围**：这一版明确**不做什么**？
5. **界面**（有页面时才问）：照设计稿做，还是照规范做？

## 步骤 3：把决定写进文件

当场写，不要攒到最后批量补。

### 写入 `docs/spec.md`

```markdown
# 本版规格：<一句话说清这版做什么>

## 做完长什么样
<用用户能验收的话描述行为，不写实现细节、不写文件路径>

## 验收清单
- [ ] <可勾选的、看得见的结果>
- [ ] ...

## 这一版明确不做
- <排除项，防止范围蔓延>

## 需要改动的地方
- <模块/接口层面。不写具体文件路径，路径会过期>
```

**不要写文件路径和代码片段。**它们今天对、明天就过期，反而变成误导。

### 写入 `AGENTS.md`

```markdown
# 项目宪法

## 怎么看懂这个项目
<构建命令、测试命令、目录地图，最多 20 行>

## 红线（越过就算错）
- <例：禁止在业务代码里直接 new 数据库连接>
- <例：禁止新增一个和现有重复的工具函数>

## 术语
<只写项目特有的，通用编程概念不写>
```

## 步骤 4：判断要不要写 ADR

三条**全部**满足才写，缺一条就不写：

1. **难以逆转**——以后改主意成本明显
2. **无上下文时令人意外**——后来的人会问「为什么这么做」
3. **真实权衡的结果**——确实有别的选项，因为具体理由才选了这个

```markdown
# <决定的一句话>

<1–3 句：什么情况、决定了什么、为什么这么定。>
```

**ADR 可以就写一个段落。**价值在于记下「做过这个决定」和理由，不在于填满章节。

## 完成标准

- [ ] `AGENTS.md` 存在且已写清红线与构建/测试命令
- [ ] `docs/spec.md` 存在，验收清单每条都看得见、可勾选
- [ ] 「这一版不做的事」不为空
- [ ] 每一个需要问用户的问题都问过了，且带了推荐答案
- [ ] 满足 ADR 三条的才写了 ADR，没满足的没写
- [ ] **用户已确认达成共识**——没有这句，不要进入 build

## 常见跑偏

- **把进展写成文档。** 对齐产出的是「决定」，不是「记录我们干了什么」。
- **spec 里塞实现。** spec 写「用户能撤销已提交的订单」；不写「在 Order 实体加 status 字段」。
- **宪法写成百科。** `AGENTS.md` 超过一屏就该砍——它每次会话都要加载，臃肿就是浪费。
- **没确认就开工。** 跳过确认是这套体系唯一真正致命的事。

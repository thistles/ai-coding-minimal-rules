# 造：竖切片，一次一片

**"造"的单位不是"任务"，是"一条能独立验证的完整路径"。**

一条竖切片 = 从数据到界面全打通的最小闭环，做完就能演示、能验收。
横着写（先把所有模型写完、再写所有接口、再写所有界面）是失控的头号来源。

## 开工前

1. 读 `AGENTS.md` —— 红线是什么
2. 读 `docs/spec.md` —— 验收清单是什么
3. 读 `docs/adr/` —— 有没有约束到你这块的既定决定

## 步骤 1：选缝（seam）

**缝 = 你能观察行为、又不用钻进里面的那个公共接口。**

测试只写在缝上，不测内部实现。

- 优先用**已经存在**的公共接口。
- 需要新缝时，**在尽可能高的层**开缝。缝越少越好，理想是一个。
- 缝的位置要跟用户确认过。没确认过的缝，不许写测试。

问一句就能定：**"这块对外的公共接口是什么？我们测哪几个？"**

## 步骤 2：红

先写一个失败的测试，只写这一个。

- 名字写**行为**不写实现：`用户能用有效购物车结账`，不写 `checkout 调用了 process`。
- 期望值必须是**独立的已知真值**（一个手算例子、一个字面量、规格里的一条），不能拿实现的算法再算一遍——那是同义反复，永远不会失败。
- 亲眼看它变红。**没变红说明它没测到东西，先修测试。**

## 步骤 3：绿

只写让这一个测试通过的代码。不许顺手实现下一个功能，不许加"以后可能用得上"的分支。

跑：单测文件 → 类型检查 → 循环。

## 步骤 4：下一片

重复 2–3。每一片都是一颗**曳光弹**：穿过全部层，能看见它落在哪。

重构**不属于**这个循环。它属于验收阶段。

## 步骤 5：收尾

- 类型检查通过
- **全量测试跑一遍**——不是最后一次才跑，是每次收尾都跑
- 对着 `docs/spec.md` 的验收清单逐条核对
- 提交信息写清「为什么」，不是「改了什么」

## 硬规则

### 爆炸半径超 5 个文件 → 停下来

一次改动要碰超过 5 个文件时，**不要直接改**。改走**扩展-收缩**：

1. **扩展**：把新形态加在旧形态旁边，此时旧代码仍能工作
2. **迁移**：按目录/包分批把调用点挪过去，每批都是一次提交，每批之后都是绿的
3. **收缩**：确认没有调用方了，删掉旧的

（大范围重命名、改共享类型、换字段结构，都属于这一类。硬改一次就是"改一处错三处"。）

### 不许改范围外的东西

发现一个 spec 之外的 bug / 一段该重构的代码 / 一个顺手能优化的地方：

- **不要动它。**记下来，告诉用户，让他决定。
- 混进本次改动的每一处"顺手"，都是后面查不清的耦合源。

### 手上有明确的活没干完，不许开新的

一条切片绿灯 → 立刻进入下一条。不要在"顺手优化"的沼泽里漂着。

## 完成标准

- [ ] 每一条验收清单都有对应的绿灯测试
- [ ] 测试只从公共接口观察行为，没有断言内部调用次数
- [ ] 期望值来自独立来源，不是拿实现再算一遍
- [ ] 类型检查通过
- [ ] 全量测试通过
- [ ] 改动文件数 ≤ 5，或走了扩展-收缩并保持每步都是绿的
- [ ] 本次改动没有 spec 之外的内容
